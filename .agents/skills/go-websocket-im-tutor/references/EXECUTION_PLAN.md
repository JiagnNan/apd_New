# 固定执行计划 v2：Go WebSocket → go-zero 自研 IM

**唯一权威执行清单。不得因为对话变化重新发明课程或跳过验收。** 本计划是一次完整项目的分阶段交付，不是按天安排的长期打卡表。按任务 ID 顺序推进；任一任务未过验收，下一项不能标记完成。

## 开发目标与边界

- 必做：L01–L13；选修：L14 多节点。总课数 14。
- 最终最低交付：登录/连接鉴权、单聊、会话成员校验、数据库存储、ACK、幂等重试、离线补拉、正确关闭与并发测试。
- 不在第一版：语音视频、群管理高级权限、撤回编辑、搜索、表情/文件存储、端到端加密、K8s、百万连接、高级离线推送。此类需求单独排期，不可混入基础课。
- 测试始终贯穿各课，L13 是集中复核而不是到那时才写测试。
- 建议 Demo 实验位置 `api-gateway/cmd/ws-lab`（直接复用 `api-gateway` Go Module），到 L08 再集成主程序；实际路径先核对，避免随意加 Go Module、修改 go.work。

## 启动前先核对的事实（G0）

- `go.work` 是否仍是 `api-gateway`、`server`、`commonlib`、`grpcclient`；不要假设项目仍处于上一轮 GitHub 的状态。
- `api-gateway/internal/svc/servicecontext.go` 是否已经接入 Auth RPC；`auth` Logic 是否真正实现登录与 JWT 验证；新增 WS 前先记录依赖与认证方案。
- `goprobuf/auth/auth.proto` 的 `go_package` 和生成目录，L09 的 IM Proto 要遵循统一规则，不复制同名生成包。
- 每次只按需启动必需依赖。Demo 不要求启动 Etcd/MySQL；集成时根据真实依赖启动 Gateway、Auth RPC、IM RPC、MySQL 等。

## 教学运行协议（Codex 每次必遵守）

1. `状态核对`：读 `learning/websocket/PROGRESS.md`，如不存在引用进度模板创建；读当前任务的课程细则、计划行和项目约束，不加载下一课。
2. `精准讲解`：仅本任务必要的机制、API 及失败行为，不超过约 5 句机制解释；具体到本仓库文件和函数，无法确认时先查看。
3. `学生动手`：先给输入/输出/边界，不直接整段输出完整实现。代码生成与文件修改应根据用户授权。
4. `验收和追问`：检查可核实的代码及执行输出；至少让学生解释一个关键设计取舍。若不合格，给最小修复建议与复测命令。
5. `记录与解锁`：PASS 时写进度（若权限允许）、列出证据，然后告知下一任务 ID，但**不提前讲下一任务的内容**。若 BLOCKED，保留 ID 和阻塞原因。

## 通用检查清单

- 编译：所在模块内 `go test ./...` 或只测相关包；必要时 `go build ./...`。
- 并发：`go test -race ./...`，明确测试机器环境和适用条件；在 Windows 若 CGO / C 编译器未配置，标环境阻塞并提供解决建议。
- 失败路径：握手失败、非法消息、无权限、离线接收人、队列满、读写超时、重复投递、服务重启。
- 资料：只以真实源码和测试证据认定完成；写出关键命令的执行位置，禁止假装验证过。
- 只改当前任务涉及目录；检查 `git diff --check` 和与本任务无关的差异。
