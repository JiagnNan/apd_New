# 逐课教学大纲：Go WebSocket → go-zero IM

仅在用户要求课程表时展示概览；每次授课只加载当前课。每课的目标是可验证的最小成果，不承诺固定天数。课程顺序可在有证据的前提下调整。

## 第一阶段：单机 WebSocket 基础（L01–L07）

### L01：HTTP Upgrade 与 Echo Server
- **前置**：会写 `net/http` Handler，知道 HTTP 请求/响应。
- **只讲**：WebSocket 握手、101 状态、`ws`/`wss`、`Upgrader.Upgrade`、`ReadMessage` 和 `WriteMessage`；HTTP Upgrade 之后的连接生命周期。
- **自己做**：独立的小 Demo，仅注册 `/ws` 路由，客户端发一条 text，服务端原样回显；解释一次 Upgrade 后为何不需要每条消息重新 HTTP 请求。
- **验收**：浏览器开发者工具或 WS 客户端见到 `101 Switching Protocols`；可来回发 3 条消息；断开后服务端读循环退出；错误握手被拒绝。
- **常见错误**：混用 HTTP 响应和 WebSocket 写入；升级失败后继续使用连接；没有关闭连接；正式代码绕开 Origin 校验。

### L02：消息帧与 JSON 协议
- **前置**：L01。
- **只讲**：Text/Binary/Control 帧与应用层消息类型的区别；`encoding/json`、消息结构体和输入校验；`SetReadLimit`。
- **自己做**：设计 `type`, `requestId`, `payload` 的 JSON envelope；先支持 `echo` 与 `error` 两种业务事件；缺字段/未知类型返回错误事件。
- **验收**：正常消息可解析；非法 JSON、未知事件、超限消息按协议处理且服务不崩溃。
- **常见错误**：把 `websocket.TextMessage` 当作自己的业务 type；客户端可控字段未经校验；无限制读取消息。

### L03：Goroutine、Channel 与单写者模型
- **前置**：L02，理解 Goroutine/Channel 基本语法。
- **只讲**：一个连接的 `readPump`、`writePump`，谁拥有写权限、有界 `send` Channel、`select` 和退出传播。
- **自己做**：为每个连接拆分独立读、写循环；所有业务消息只进有界发送队列；写循环是唯一常规写者。
- **验收**：连续快速发送时无并发写 panic；正常关闭时两个循环退出；发送队列满时行为明确（如关闭慢连接）。
- **常见错误**：多个 goroutine 直接 `WriteJSON`；关闭了仍有写入者的 channel；死循环空转；goroutine 泄漏。

### L04：Hub、map、并发安全与定向推送
- **前置**：L03。
- **只讲**：Hub 管理注册/注销，`map[userID]map[connID]*Client`，`Mutex/RWMutex` 与单 owner 事件循环两种保护策略的选择。
- **自己做**：两个浏览器分别作为 A、B，A 发消息，服务端只推给 B；同用户两连接均收到消息。
- **验收**：并发注册/注销与推送不产生 map 数据竞争；断线后在线连接数正确；用户 B 不在线有明确处理。
- **常见错误**：无锁 map；把业务逻辑嵌入 Hub；广播泄露给其他用户；持有锁进行慢网络写入。

### L05：Ping/Pong、超时、断线和优雅退出
- **前置**：L03–L04。
- **只讲**：Ping、Pong、`SetReadDeadline`、`SetPongHandler`、`SetWriteDeadline`、`time.Ticker`；关闭顺序。
- **自己做**：服务端定期 Ping、收到 Pong 延长读取期限；客户端主动关闭或网络断开时移除 Hub 连接。
- **验收**：正常连接保持；模拟异常断线后最终回收；重连后没有重复的旧连接；关闭服务无明显 goroutine 残留。
- **常见错误**：只设置 PongHandler 但不调用读循环；deadline 错配；Ticker 没停止；退出时重复 close。

### L06：连接认证与授权边界
- **前置**：L05；理解 JWT 基本校验。
- **只讲**：握手身份、令牌有效期、Origin 检查、用户 ID 与客户端字段隔离、登出及权限失效处理。
- **自己做**：未授权握手拒绝；授权握手绑定可信 `userID`；尝试伪造 `senderId` 不能改变发送者身份。
- **验收**：无凭据、过期凭据、错误 Origin 均拒绝；跨用户伪造被拒绝；会话撤销后的策略明确。
- **常见错误**：只解析未验证 JWT；把长期 Token 放 URL；生产放开全部 Origin；浏览器假设能添加任意自定义 Header。

### L07：两人单聊协议与单机最小成品
- **前置**：L01–L06。
- **只讲**：客户端 requestId、接收方 ID、错误码、消息校验、在线投递语义。此课**不承诺消息可靠存储**。
- **自己做**：A 与 B 通过一个 Go 进程即时通讯，能显示连接/断开/投递失败状态。
- **验收**：两个用户互发；第三者不会收到；同用户多端按约定收取；无在线用户时返回可解释状态；一次连接反复发送 100 条不崩溃。
- **常见错误**：把入内存队列说成投递成功；完全相信目标用户指定的会话；无限制发送队列。

## 第二阶段：接入 apd_New / go-zero（L08–L10）

### L08：把单机 WS 接入现有 api-gateway
- **前置**：L07。
- **只讲**：检查工作区 HTTP 入口、路由、ServiceContext；通过受控路由注册 WS Handler，不手改 goctl 生成的 `routes.go`。
- **自己做**：在现有 `api-gateway` 注册 `/ws` 路由；HTTP 登录接口保持现状；避免新增独立 WS 服务进程。
- **验收**：原 HTTP 接口仍可访问；`/ws` 握手成功；`go test` / `go build` 无编译错误；Git diff 不包含无关改动。
- **常见错误**：未经检查假设 `ServiceContext` 已有 Auth RPC；修改生成文件；路由与端口冲突。

### L09：IM Proto、IM RPC 与职责边界
- **前置**：L08；会使用项目当前的 `.proto` 和 goctl 代码生成方式。
- **只讲**：Gateway 管连接、IM RPC 管业务；请求字段传递、context deadline、错误映射、Proto 兼容。先检查仓库实际 `go_package`/生成路径。
- **自己做**：最小 `SendMessage` RPC，验证参与者与参数，先用假 Repository；调用方能够分清持久化结果和实时推送结果。
- **验收**：API Gateway → IM RPC 可以成功调用并返回明确错误；断开 IM RPC 时不会卡死请求；不会无理由拆出多个 RPC。
- **常见错误**：长连接在业务 RPC 内管理；API 与 RPC 双重维护同一份状态；直接信客户端发送者 ID。

### L10：MySQL 会话与消息持久化
- **前置**：L09；掌握基础 MySQL 索引/事务。
- **只讲**：`im_conversations`、`im_conversation_members`、`im_messages` 的必要字段、唯一索引、会话授权和消息事务边界。
- **自己做**：消息经过权限校验后保存；按会话、消息 ID 游标拉取历史；不允许非成员拉取。
- **验收**：断线再连接可查历史；越权会话请求失败；索引及查询顺序可解释。
- **常见错误**：先推送再把未保存消息报告为发送成功；只靠客户端传 sender ID；不做会话成员校验。

## 第三阶段：可靠性、测试与扩展（L11–L14）

### L11：ACK、客户端重试与幂等
- **前置**：L10。
- **只讲**：ACK 的三种不同语义；`clientMsgId` 与 `(sender_id, client_msg_id)` 唯一约束；重复请求返回同一逻辑消息结果。
- **自己做**：在模拟超时后重复提交相同客户端消息 ID；服务端只有一条消息记录。
- **验收**：高频重复请求不造成重复存储；发送者知道“已保存”而不是错误声称“对方已读”。
- **常见错误**：靠内存 map 去重；先 ACK 再提交数据库；处理唯一冲突不查询已有结果。

### L12：离线消息、游标补拉与顺序
- **前置**：L10–L11。
- **只讲**：离线恢复以数据库为事实来源、历史分页游标、排序键选择、同一会话内可解释的顺序保证。
- **自己做**：B 离线，A 发 3 条；B 重连后拉回未收到的数据；分页没有重复或缺漏（在明确一致性边界下）。
- **验收**：重连补拉成功；分页稳定；客户端重复接收可用 message ID 去重。
- **常见错误**：误把 Redis Pub/Sub 当可靠消息存储；用 OFFSET 丢失排序稳定性；宣称跨实例全局严格顺序。

### L13：安全、测试与负载验证
- **前置**：L01–L12 中本次所用功能。
- **只讲**：单测、集成测试、`go test -race`、消息大小、认证、限流、慢客户端、goroutine 退出与可观测指标。
- **自己做**：准备 10–100 个测试客户端（先从 10 开始）；进行连接/断线/乱序/恶意输入的回归；记录 CPU、内存、goroutine 与错误率。
- **验收**：测试证据明确列出环境、并发数、消息数量、失败数；未实际压测不宣称大规模容量。
- **常见错误**：把 race detector 的工具链环境错误当作竞态；只测成功路径；没有限流和有界资源。

### L14：多实例设计（**进阶选修，不是 MVP 前置**）
- **前置**：L13，已有单机稳定证据。
- **只讲**：节点标识与用户路由、Redis 状态 TTL、跨节点推送、断连补拉、消息路由与可靠性边界；何时采用队列/Outbox。
- **自己做**：设计两节点：A 连接节点 1，B 连接节点 2，证明路由可达；杀掉一个节点后能重连与补拉。
- **验收**：跨节点可投递；节点离线状态最终清理；Redis Pub/Sub 中断时可依靠 DB 补拉，不作“绝对不丢”承诺。
- **常见错误**：过早加 RabbitMQ；把在线状态当强一致；把跨节点实时消息与持久化事务等同。

## 推荐节奏与判定

- 建议每节：机制 5–10 分钟、动手 20–60 分钟、验收 10–20 分钟；难课可以拆成 Lxx-a/Lxx-b，不以分钟数硬压内容。
- 必须能说出关键调用链、代码所有者与失败路径；通过验收再标为完成。
- 学生缺乏前置 Go 并发知识时，只补「当前代码必需」的 `go`、Channel、select、Mutex，不把整门 Go 基础课插进来。
- 默认本机按需启动：早期只运行独立 Demo；接入时按业务启动 API Gateway、Auth RPC、IM RPC 及必要的 MySQL/Etcd/Redis。先检查真实依赖，不自动启动所有服务。
